# Source Intake Audit — первая волна источников

Дата аудита: 2026-05-17
Статус: proposal / требует пользовательской проверки перед изменением реестров
Контур: техническая библиотека источников и подготовка дополнительных агентов

## 1. Назначение

Этот документ фиксирует первую рабочую инвентаризацию после загрузки большой волны материалов в проект «Пишем книгу».

Цель не в том, чтобы объявить все материалы рабочей библиотекой. Цель — отделить:

1. источники, уже представленные в реестрах;
2. источники, которые есть в загруженной волне, но не имеют отдельной карточки;
3. дубли и альтернативные версии одного источника;
4. проектные документы, которые нужно синхронизировать как живые правила проекта;
5. источники, из которых действительно имеет смысл выводить новых агентов.

Главное правило: источник не становится рабочим только потому, что его название появилось в проекте. Рабочий статус появляется только после связки: материал → карточка → роль → разрешённое применение → запреты → зоны книги/продукта → агентные слои → next_action.

## 2. Уже существующая инфраструктура

Проверены файлы:

- `knowledge/00_manifest/sources.registry.json`
- `knowledge/03_source_books/source-locations.registry.json`
- `knowledge/03_source_books/source-location.template.md`
- `knowledge/04_processed/source_cards/14_waltman_codd_macfarr_moore_socratic_questioning.md`
- `knowledge/04_processed/source_cards/44_agent_specs_card.md`

Вывод:

- `sources.registry.json` уже содержит широкий набор первичных source cards: MLM-книги, КПТ, Сократ, SuperBetter, проектные методы, MVP, Своды, карты и style/profile cards.
- `source-locations.registry.json` уже задаёт безопасную схему: raw books, Drive URLs и Drive file IDs не коммитятся; используются только имена файлов, статусы доступа и правила применения.
- `source-location.template.md` задаёт правильные запреты: не коммитить PDF/сканы/сырой текст, не делать вид, что источник прочитан, если доступна только карточка или placeholder.

Проблема:

- новая волна загруженных в проект файлов шире, чем текущие реестры;
- часть источников уже покрыта общими карточками, но не как отдельные источники;
- часть проектных документов в `source-locations.registry.json` помечена как `not_registered`, хотя в текущем проектном контуре появились загруженные версии;
- есть риск создать агентов раньше, чем проверены источники, на которых они должны стоять.

## 4. Предварительный порядок аудита

Правильная последовательность:

1. Сначала проектные living documents: Свод, Плотниковский мотор, Paket v20, Карта контекстов, MVP, глава 30 design.
2. Затем сократический блок: Уолтман/Кодд/Макфарр/Мур, Фарнсворт, Оверхолзер.
3. Затем КПТ-блок: Джудит Бек, Аарон Бек CT-R, Камалетдинова/Антонова, Харитонов, Фриман/Девульф, тревожный workbook.
4. Затем этика влияния: Чалдини.
5. Затем эмоциональный и ролевой слой: Илсе Санд, Эрик Берн, Байрон Кейти.
6. Затем геймификация и маршрут: SuperBetter + MVP.

Почему так: сначала нужно привести в порядок правила самого проекта, иначе внешние книги начнут тащить систему в разные стороны.

## 5. Агенты: создавать не всех сразу

`source_intake_auditor`

Назначение: проверять источник перед включением в рабочую библиотеку.

Почему нужен первым: без него остальные агенты будут опираться на неаудированные материалы.

## 6. Ближайший технический PR

Минимально правильный PR должен сделать не массовую перестройку, а один безопасный шаг:

1. добавить этот audit artifact;
2. добавить proposal `source_intake_auditor`;
3. не менять пока `sources.registry.json` и `source-locations.registry.json` массово;
4. не создавать новые source cards до проверки этого плана Сергеем.

После принятия:

1. создать карточки для отсутствующих источников пачкой 1;
2. обновить source-locations registry без Drive IDs/URLs;
3. завести `source_intake_auditor` как рабочий agent spec или internal layer;
4. только потом переходить к агентам второго ряда.

## 7. Риски

1. Слишком раннее создание агентов даст видимость системы без проверенного основания.
2. Цитатные сборники и self-help книги могут выглядеть убедительно, но их нельзя использовать как доказательную базу без проверки контекста.
3. КПТ-материалы легко превращают книгу в терапию; для проекта они должны быть линзами мышления и бережного сопровождения, а не клиническим протоколом.
4. Чалдини нужен как guardrail против манипуляции, а не как учебник давления.
5. Сократический метод нужен как фонарь ясности, а не как поводок к нужному решению.

## 8. Решение, которое требуется от Сергея

Предлагаемое решение:

- принять этот порядок аудита первой волны;
- первым создать `source_intake_auditor` как служебный агент/слой;
- не создавать остальные агенты до аудита их источников;
- следующей задачей открыть PR на карточки отсутствующих источников и синхронизацию living project docs.
