# Source Library Maintenance Protocol

Этот файл описывает, как поддерживать приватную библиотеку источников Google Drive и committed source cards в GitHub в согласованном состоянии.

## Принцип

GitHub хранит не raw books, а карточки, правила, статусы и обработанные артефакты.

Google Drive хранит приватные полные материалы, внутренние документы проекта и рабочие спецификации.

Агент не имеет права делать вид, что прочитал материал, если в GitHub есть только source card, placeholder, пустой Google Doc или архивный дубль.

## Типы материалов

### 1. Внешние книги и PDF

Примеры:
- `plotnikov_reasonable_network_marketing.pdf`
- `gerber_e_myth.pdf`
- `mcgonigal_superbetter.pdf`
- `judith_beck_cbt.pdf`

Правило: использовать только после целевого чтения нужного фрагмента. Не коммитить сырой текст, длинные цитаты, сканы или PDF.

### 2. Внутренние проектные документы

Примеры:
- `practical_mlm_ecology_framework`
- `idea_amplifier_framework`
- `frequency_language_card`
- `quiet_master_framework`
- `quest_chapter_framework`

Правило: эти документы можно развивать как источник правил проекта. После существенного изменения нужно решить, обновлять ли corresponding source card в GitHub.

### 3. Живые управляющие документы

Примеры:
- Свод проекта
- Карта источников проекта
- Карта контекстов источников
- MVP-документ
- Паспорта агентов
- Пакеты синхронизации и обновлений

Правило: это не архивные файлы. Они должны обновляться после крупных изменений в книге, MVP, workflow или агентной системе.

### 4. Placeholder-документы

Примеры:
- документ создан с правильным названием, но был пустым;
- документ содержит seed-спецификацию из source card, но ещё не проверен как полноценный источник.

Правило: не считать placeholder внешним источником. Статус должен оставаться `seeded_from_source_card` или `content_not_verified`, пока человек не подтвердит содержание.

### 5. Архивные дубли

Примеры:
- `field_three_act_structure.docx` при наличии нативного `field_three_act_structure`;
- `idea_amplifier_framework.docx` при наличии нативного `idea_amplifier_framework`.

Правило: если есть нативный Google Doc и одноимённый `.docx`, основным считается нативный Google Doc. `.docx`-дубль не использовать как source location и не индексировать агентами.

Если `.docx`-дубль пустой, перенос не нужен.

Если `.docx`-дубль содержит текст, нужно проверить, есть ли этот текст в нативном Google Doc. Если нет — перенести вручную или через безопасный инструмент. Если дословный перенос блокируется, зафиксировать это в основном документе и в `archived-duplicates.registry.json`.

## Когда обновлять Google Drive

Обновлять Drive-документ нужно, если:
- меняется правило проекта;
- появляется новая формула, которую нужно сохранить как рабочую норму;
- source card в GitHub стал слишком коротким для дальнейшей работы;
- материал нужен агентам как самостоятельная методическая рамка;
- после review главы появились новые устойчивые правила.

## Когда обновлять GitHub

Обновлять GitHub нужно, если:
- изменился статус доступа к источнику;
- появился новый private Drive документ;
- источник из `not_found_in_private_folder` стал доступен;
- изменилось правило использования источника;
- появился новый active decision;
- изменился `nextAction` проекта;
- найден архивный дубль, который нужно исключить из будущей индексации.

## Что нельзя делать

- Не хранить private Drive file IDs в публичном GitHub.
- Не хранить private Drive URLs в публичном GitHub.
- Не переносить raw books в репозиторий.
- Не обновлять source card автоматически после каждого мелкого изменения в Google Doc.
- Не считать Google Doc достоверным, если он создан как пустая заготовка и не прошёл review.
- Не индексировать `.docx`-дубли, если для того же source_id есть нативный Google Doc.

## Рекомендуемый цикл обновления

1. Изменился материал в Google Drive.
2. Проверить: это внешняя книга, внутренний проектный документ, живой управляющий документ или архивный дубль.
3. Если это внутренний/живой документ, обновить его статус в `source-locations.registry.json`.
4. Если это архивный дубль, добавить его в `archived-duplicates.registry.json` и исключить из будущей индексации.
5. Если изменение влияет на поведение агентов, обновить source card в `knowledge/04_processed/source_cards/`.
6. Если изменение влияет на resume, обновить `project-state.json` и `project-state.md`.
7. Если изменение влияет на ручную проверку, обновить `review-index.md`.

## Правило Плотникова

Полный Плотников в private Drive нужен как дальняя карта маршрута: понимать последовательность, дозировку, будущие темы и границы преждевременного объяснения.

Он не разрешает пересказ, близкий рерайт, копирование структуры, длинные цитаты или перенос авторской самопрезентации в нашу книгу.
