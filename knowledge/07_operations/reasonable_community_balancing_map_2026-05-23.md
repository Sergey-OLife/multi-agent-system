# Reasonable Community balancing map

Status: operations_note / archive-derived insight
Date: 2026-05-23
Source: PR #269 — Archive hundred mutations reading discipline

## 1. Purpose

This note preserves the compressed result of the 100-mutation archive analysis.

The goal is not to store all mutations.

The goal is to preserve the method that made the archive useful:

```text
Layer -> distortion -> Sergey correction -> new form -> what it saved -> what it could damage -> safeguard.
```

Use this note as a working interpretive aid when reading large project archives, especially book/product archives where later documents are not merely newer, but often exist to correct a specific distortion in earlier work.

## 2. Core finding

The Reasonable Community project matures not by adding more ideas, but by balancing strong layers before they become new distortions.

A strong layer can become a new problem when it takes too much authority:

- Plotnikov motor can become pressure.
- Svod ethics can become cautious fog.
- Scene can scatter the law of the chapter.
- MVP can start commanding the book.
- Mentorship can become dependency.
- Archive can become false authority.
- Assistant speed can become smooth imitation of understanding.

The mature move is not to delete strong layers, but to give each layer a counterweight and a boundary.

## 3. Main balancing conflicts

1. Authorship vs. summary/retelling.
2. Action vs. cautious ethics.
3. Person vs. deal.
4. Mentorship vs. dependence.
5. Psychology vs. therapy.
6. Scene vs. lecture.
7. One strike per chapter vs. thematic richness.
8. Ethics vs. soft fog.
9. Book vs. product/MVP.
10. Gamification vs. training pressure.
11. Archive vs. false memory.
12. Assistant vs. smooth imitation of understanding.

These conflicts should not be flattened into a single hierarchy such as “newer document wins.”

For each conflict, first ask what distortion the later layer was created to cure.

## 4. Archive-reading rule

When reading a large archive, do not only search for the latest continuation point.

First identify what error, distortion or loss each later layer was created to cure.

A later document may be more current, but its real value is usually diagnostic: it shows which good idea had started to damage the project.

## 5. Working procedure

Use this procedure for large archive reconstruction:

1. Identify the layer.
2. Name what existed before.
3. Name the distortion or loss that appeared.
4. Identify Sergey’s correction.
5. Name the new form that appeared.
6. Name what it saved.
7. Name what it could damage.
8. Name the safeguard that followed.

This turns archive reading from chronology into causal reconstruction.

## 6. Practical use for book work

When returning to a chapter, do not begin by asking only:

```text
What is the latest version?
```

Also ask:

```text
What did this version cure?
What did it risk breaking?
Which counterweight was added next?
```

This matters because a chapter can be technically later and still carry an overcorrection.

Examples:

- If a chapter became too cautious, return Plotnikov motor.
- If it became too aggressive, return Svod and the person.
- If it became too conceptual, return scene, object and ordinary Tuesday.
- If it became too artistic, restore the action and one law of the chapter.
- If it became too product-facing, separate book layer from MVP layer.

## 7. Practical use for archive work

When archiving a long segment, preserve the reason behind a rule, not only the rule.

A useful archive entry records:

- the correction;
- the failure pattern that made it necessary;
- the boundary it created;
- the open loop it leaves behind.

Do not turn archive into project-state, checkpoint, roadmap, approval authority or implementation record.

Archive explains origin and context. It does not command current state by itself.

## 8. Practical use for assistant behavior

A user correction should not be treated as a local preference until the violated project principle is identified.

When Sergey reacts sharply, the assistant should first look for a system defect:

- service language entered reader text;
- a chapter lost its one strike;
- morality replaced action;
- a strong source became visible instead of being melted;
- the assistant reported completion before verification;
- archive was read flatly instead of causally.

The correct response is not merely “fix the sentence.”

The correct response is:

```text
Which repeated failure pattern did this expose?
What rule or procedure prevents it next time?
```
