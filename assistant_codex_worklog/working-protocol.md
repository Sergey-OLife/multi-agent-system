# Working Protocol — Assistant × Codex

Этот файл фиксирует правила работы между Сергеем, ChatGPT и Codex.

## Основной принцип

ChatGPT помогает формулировать задачи, проверять результаты Codex, удерживать логику проекта и предотвращать хаос.

Codex выполняет конкретные изменения в репозитории через отдельные PR.

GitHub — источник правды по коду, структуре, состоянию проекта и рабочим артефактам.

## Работа с уже подключённым GitHub

Если в начале чата репозиторий уже подключён, ChatGPT дальше не задаёт повторный вопрос о подключении.

Правильный порядок:
- использовать доступный GitHub-инструмент;
- проверять состояние репозитория через реальные tool calls;
- если tool call вернул ошибку, сообщить конкретную ошибку и что именно не удалось выполнить;
- не просить Сергея заново подтверждать само использование GitHub в рамках текущего чата.

Это правило не отменяет approval-gates: для смысла книги, логики агентов, материалов от имени Сергея и workflow-переходов всё равно требуется явное согласие на само действие.

## Быстрая команда сохранения

Команда:

```text
#checkpoint full
```

означает: сохранить полную текущую рабочую точку.

При выполнении checkpoint нужно обновить:

- `assistant_codex_worklog/current-state.md`;
- `assistant_codex_worklog/roadmap.md`;
- `assistant_codex_worklog/decision-log.md`;
- при необходимости `assistant_codex_worklog/working-protocol.md`;
- при необходимости `assistant_codex_worklog/restart-prompt.md`.

Цель: чтобы при обрыве связи, перегрузе чата или переходе в новый чат можно было продолжить без потери контекста.

## Как работать с PR

1. Если предыдущий PR смержен, следующая веха — новая задача Codex.
2. Если PR открыт и нужно исправить комментарий reviewer, это ответ в текущий Codex-чат, не новая задача.
3. Если Codex пишет, что PR создан, но ссылка не видна, нужно нажать кнопку `Создать PR` в той же задаче Codex.
4. Нельзя создавать два PR на один и тот же баг.
5. После каждого PR нужно проверять:
   - есть ли PR реально в GitHub;
   - mergeable ли он;
   - нет ли draft;
   - какие файлы изменены;
   - прошли ли build/typecheck/tests;
   - не добавлены ли raw book files.

## Обязательная двойная самопроверка PR

После создания каждого PR ChatGPT обязан выполнить двойной self-review до того, как отдаёт PR Сергею как готовый к проверке.

### Pass 1 — техническая проверка

Проверить:
- PR реально открыт в GitHub;
- `mergeable` не указывает на конфликт;
- PR не находится в draft, если draft не был запрошен явно;
- изменены только ожидаемые файлы;
- `project-state.json` и `project-state.md` синхронизированы, если меняется состояние проекта;
- baseline/tests обновлены вместе с изменением состояния;
- raw books, PDF/EPUB/DJVU/MOBI и сырой текст источников не добавлены;
- private Drive URLs и file IDs не попали в репозиторий.

### Pass 2 — смысловая проверка

Проверить:
- PR не перескакивает workflow-стадии;
- draft не превращается в reviewed/approved без явного пользовательского разрешения;
- review-map не меняет сам draft без approval;
- новые правила не противоречат Своду, project-state и review-index;
- формулировки не создают ложного статуса вроде «источник прочитан», если есть только source card или placeholder;
- нет новой красивой риторики вместо реального правила.

### Если найдена ошибка

1. Оставить top-level comment в PR с пометкой `Self-review pass N` и коротким описанием проблемы.
2. Исправить проблему в той же ветке PR.
3. Повторно проверить PR после исправления.
4. Только после этого дать Сергею ссылку, статус mergeability и список того, что уже проверено.

Запрещено отдавать PR как готовый, если он не прошёл две проверки или если известная ошибка ещё не исправлена.

## Ограниченное право ChatGPT на merge

ChatGPT может самостоятельно выполнить `Merge pull request → Confirm merge` только для технических PR после обязательной двойной самопроверки.

Разрешённые категории для самостоятельного merge:
- техническая синхронизация `project-state` и его зеркала;
- исправление тестов, baseline assertions и CI-совместимости;
- обновление служебных протоколов, если они не меняют смысл книги, логику агентов или пользовательские материалы;
- реестры, индексы, ссылки, review queue и другие инфраструктурные файлы;
- review-map, если он не меняет сам draft и не добавляет новый смысл от имени Сергея.

ChatGPT не имеет права мержить без явного согласия Сергея, если PR:
- меняет смысл книги, draft, reviewed chapter или approved chapter;
- меняет логику агентов, маршруты, guardrails или поведение системы;
- добавляет в материалы новые утверждения, позицию, голос, обещания или формулировки от имени Сергея;
- создаёт или меняет source card, training case, Свод, карту контекстов, MVP-документ или другой смысловой материал;
- переводит артефакт на следующую workflow-стадию;
- содержит спорную редакторскую, этическую, богословскую, маркетинговую или продуктовую рамку.

Если категория PR смешанная, применяется более строгий режим: без явного согласия Сергея merge запрещён.

Короткое правило: техническое можно ускорять; смысл, агентную логику и материалы от имени Сергея — только через явное approval.

## Как отвечать Сергею

В ответах нужно давать кликабельные ссылки на GitHub-файлы, а не только пути.

Особенно для:

- review-index;
- human-review-guide;
- plotnikov map;
- sync package;
- project-state;
- source registry;
- assistant worklog files.

## Язык артефактов

- Технические metadata keys могут быть на английском.
- Human-readable content должен быть на русском.
- Reviewer-facing объяснения должны быть на русском.
- Reader-facing текст будущей книги должен быть на русском.

## Работа с книгами и источниками

- Полные книги не коммитить в GitHub.
- Сырой текст Плотникова не коммитить.
- PDF/EPUB/DJVU/MOBI не добавлять в репозиторий.
- Source card — это инвентарь, не сама книга.
- Если полного материала нет, агент не должен делать вид, что читал источник.
- Для полного материала использовать ручную загрузку фрагмента или приватный Google Drive.

## Работа с Плотниковым

Порядок обработки:

1. manual upload одной главы или предисловия;
2. plotnikov map;
3. sync package;
4. user review;
5. chapter draft только после approval;
6. reviewed chapter;
7. approved chapter только после явного approval;
8. update package.

Запрещено:

- пересказывать Плотникова;
- делать близкий рерайт;
- копировать структуру предисловия/главы;
- использовать длинные цитаты;
- строить нашу авторитетность на трофеях, доходах и «я успешный, слушай меня».

## Стиль проекта

- Не использовать выражение `христианское собрание` в книге.
- Использовать широкие формулировки: `духовная сфера`, `личные убеждения`, `пространство доверия`.
- `Каленчевский голос воодушевления` заменён на `Тихий Мастер`.
- Голос проекта: ясность, спокойная сила, границы, служение без давления.

## Перезапуск чата

Если чат перегружен:

1. Новый чат не должен восстанавливать контекст по старой памяти.
2. Главный источник правды — GitHub.
3. Начинать с `assistant_codex_worklog/restart-prompt.md`.
4. Затем открыть:
   - `assistant_codex_worklog/current-state.md`;
   - `assistant_codex_worklog/roadmap.md`;
   - `assistant_codex_worklog/working-protocol.md`;
   - `knowledge/00_manifest/project-state.md`;
   - `knowledge/05_agent_memory/review_queue/review-index.md`.

## Что делать после отдыха

1. Проверить review-index.
2. Открыть map и sync package по `chapter_00_preface`.
3. Дать решение: approve / правки / reject.
4. Не начинать draft без явного approval.
