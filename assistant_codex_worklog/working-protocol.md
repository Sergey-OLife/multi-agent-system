# Working Protocol — Assistant × Codex

Этот файл фиксирует правила работы между Сергеем, ChatGPT и Codex/GitHub.

## Основной принцип

ChatGPT помогает формулировать задачи, проверять результаты Codex, удерживать логику проекта и предотвращать хаос.

Codex/GitHub выполняет и фиксирует конкретные изменения в репозитории через отдельные PR.

GitHub — источник правды по коду, структуре, состоянию проекта и рабочим артефактам.

## Обязательные protocol addenda

При запуске или перезапуске чата вместе с этим файлом нужно открыть и учесть все файлы из:

`assistant_codex_worklog/protocol_addenda/*.md`

Эти addenda являются частью рабочего протокола. Если addendum помечен как обязательное правило, он действует наравне с этим файлом, даже если ещё не втянут в основной текст `working-protocol.md`.

На текущий момент особенно важны:

- `restart_prompt_before_checkpoint.md` — перед `#checkpoint full` сначала дать Сергею restart prompt в чате;
- `chat_restart_prompt_length_limit.md` — чатовый restart prompt перед checkpoint должен быть до 6000 знаков с пробелами; лимит не относится к файлу `restart-prompt.md`;
- `plus_approval_shorthand.md` — `+` означает продолжение без approval, `++` означает approval текущего понятного approval-gate;
- `auto_mergeability_check.md` — перепроверка mergeability открытого PR не требует отдельного подтверждения.

## Book Fast Track для глав книги

Главы книги пишутся и редактируются сначала в чате, а не через цепочку PR на каждый промежуточный слой.

Правильный порядок для книги:

1. В чате создаётся или правится читательская версия главы.
2. Агенты используются как внутренние редакторские слои: `contextologist`, `svod_guard`, `plotnikov_motor`, `anti_cliche_editor`, `quiet_master`, `ethics_guard`, `frequency_language`, continuity/sync layer.
3. Сергею показывается один цельный текст и короткая редакторская записка: что изменено, что рискованно, что проверить.
4. GitHub фиксирует уже принятый результат, а не каждую промежуточную мысль.
5. Не создавать reviewed/approved дубли, если они не дают реальной редакторской пользы.

Цель: сохранить силу мультиагентной системы, но убрать бюрократию из живого письма.

## Source Intake Audit

При добавлении или проверке нового источника ChatGPT выполняет аудит источника перед включением в рабочую библиотеку.

Порядок:

1. Проверить, есть ли материал в Google Drive или в уже зарегистрированных source locations.
2. Проверить, не является ли найденный файл пустой оболочкой.
3. Проверить, есть ли карточка источника в GitHub и насколько она подробна.
4. Если материала нет, создать или предложить карточку со статусом `missing`, `placeholder` или `needs_upload`.
5. Если материал есть, проверить его пригодность: `usable_now`, `needs_enrichment`, `archive_duplicate`, `needs_native_doc`.
6. Для каждого источника указать: `usage_role`, `allowed_use`, `forbidden_use`, `book_zones`, `agent_layers`, `next_action`.

Источник не считается рабочим только потому, что он назван. Он считается рабочим, когда есть материал, карточка, роль и правило применения.

## Создание агентов из источников и логики проекта

ChatGPT может создавать отдельных агентов в любой момент, если этого требует логика проекта или если новый агент значительно улучшит качество работы.

Количество агентов не ограничивается заранее. Ограничение не числовое, а процессное: новый агент должен усиливать систему, а не плодить хаос, дублирование и лишние согласования.

Новый агент допустим, если он:

- даёт устойчивую повторяемую операцию, а не разовую идею;
- закрывает функцию, которой нет у существующих агентов;
- заметно улучшает качество книги, проверки, маршрута новичка, MVP, source intake или этического фильтра;
- не дублирует существующего агента;
- имеет понятный вход, выход, ограничения и критерии срабатывания;
- может быть описан как рабочая роль, а не как декоративная ссылка на автора, книгу или метод.

Агент может возникнуть из:

- нового источника;
- повторяющейся редакторской задачи;
- сбоя процесса;
- нового guardrail;
- нового типа проверки;
- необходимости ускорить Book Fast Track;
- необходимости разгрузить существующего агента.

Перед созданием агента нужно зафиксировать:

- `agent_id`;
- назначение;
- входные данные;
- выходные данные;
- когда вызывать;
- когда не вызывать;
- source dependencies;
- guardrails;
- связь с существующими агентами;
- риск дублирования;
- тестовый сценарий.

Если новый агент меняет маршруты, guardrails или поведение системы, требуется явное approval Сергея перед merge. Если агент создаётся как паспорт, proposal или внутренний редакторский слой без включения в маршруты, его можно подготовить без отдельного предварительного запроса, но с обязательной самопроверкой и объяснением пользы.

## Strict PR Workflow для технических частей

Строгий PR workflow обязателен для:

- кода;
- логики агентов;
- маршрутов;
- guardrails;
- tests/baseline;
- project-state;
- source registries;
- source cards;
- training cases;
- Сводов, MVP и карт контекстов;
- рабочих протоколов и restart-файлов.

## Работа с уже подключённым GitHub

Если в начале чата репозиторий уже подключён, ChatGPT дальше не задаёт повторный вопрос о подключении.

Правильный порядок:
- использовать доступный GitHub-инструмент;
- проверять состояние репозитория через реальные tool calls;
- если tool call вернул ошибку, сообщить конкретную ошибку и что именно не удалось выполнить;
- не просить Сергея заново подтверждать само использование GitHub в рамках текущего чата.

Это правило не отменяет approval-gates: для смысла книги, логики агентов, материалов от имени Сергея и workflow-переходов всё равно требуется явное согласие на само действие.

## Approval-gates

Явное approval Сергея требуется для:

- изменения смысла книги;
- изменения логики агентов;
- добавления материалов от имени Сергея;
- перехода артефакта на новую смысловую workflow-стадию;
- спорных этических, духовных, маркетинговых или продуктовых рамок.

В книжном режиме approval не должно превращаться в пять одинаковых чтений. Достаточно чётких команд:

- `принято в работу` — можно править в чате;
- `фиксируй` — можно готовить GitHub-фиксацию результата;
- `финально утверждаю главу` — можно создавать финальный approved artifact, если он нужен.

## Быстрая команда сохранения

Команда:

```text
#checkpoint full
```

означает: сохранить полную текущую рабочую точку.

Перед выполнением `#checkpoint full` обязательно сначала прислать Сергею корректный restart prompt для следующего чистого чата. Checkpoint не начинается, пока prompt не отправлен в чате.

Чатовый restart prompt перед checkpoint должен быть компактным: до 6000 знаков с пробелами. Это ограничение не относится к файлу `assistant_codex_worklog/restart-prompt.md`, который может быть подробным рабочим документом.

Чатовый prompt не должен включать большие фрагменты книги, сырой текст источников или длинный пересказ состояния проекта. Вместо этого он должен давать пути к GitHub-файлам, текущую точку, первый следующий шаг и 1–2 предложения книжного контекста только при необходимости.

При выполнении checkpoint нужно обновить:

- `assistant_codex_worklog/current-state.md`;
- `assistant_codex_worklog/roadmap.md`;
- `assistant_codex_worklog/decision-log.md`;
- при необходимости `assistant_codex_worklog/working-protocol.md`;
- при необходимости `assistant_codex_worklog/restart-prompt.md`;
- при необходимости `knowledge/00_manifest/project-state.json` и зеркало `.md`.

Цель: чтобы при обрыве связи, перегрузе чата или переходе в новый чат можно было продолжить без потери контекста.

## Как работать с PR

1. Если предыдущий PR смержен, следующая веха — новая задача/ветка.
2. Если PR открыт и нужно исправить комментарий reviewer, это ответ в текущий PR/ветку, не новая задача.
3. Если работа сделана, но PR не виден, нужно создать PR из той же ветки, а не плодить дубль.
4. Нельзя создавать два PR на один и тот же баг.
5. После каждого технического PR нужно проверять:
   - есть ли PR реально в GitHub;
   - mergeable ли он;
   - нет ли draft;
   - какие файлы изменены;
   - прошли ли build/typecheck/tests, если применимо;
   - не добавлены ли raw book files.

## Автоматическая проверка mergeability

Перепроверка mergeability открытого PR не требует отдельного подтверждения Сергея.

ChatGPT сам проверяет mergeability:

- после создания PR, если статус сначала промежуточный;
- перед просьбой о `++`;
- после `+`, если следующий безопасный шаг — проверка PR;
- после `++`, перед merge;
- если PR был открыт несколько шагов назад.

Эта проверка не является approval и не разрешает merge. Для merge всё равно нужен `++`, если PR попадает под approval-gate.

## Короткие команды Сергея

`+` означает: продолжай следующий логичный безопасный шаг по текущему плану, но это не approval.

`++` означает: approval текущего понятного approval-gate и разрешение выполнить следующий ожидаемый merge/approval action.

Если одновременно есть несколько approval-gates, `++` требует уточнения. Если пользователь пишет номер PR вместе с `++`, например `41 ++`, это approval именно этого PR.

## Обязательная двойная самопроверка PR

После создания каждого PR ChatGPT обязан выполнить двойной self-review до того, как отдаёт PR Сергею как готовый к проверке.

### Pass 1 — техническая проверка

Проверить:
- PR реально открыт в GitHub;
- `mergeable` не указывает на конфликт;
- PR не находится в draft, если draft не был запрошен явно;
- изменены только ожидаемые файлы;
- `project-state.json` и `project-state.md` синхронизированы, если меняется состояние проекта;
- baseline/tests обновлены вместе с изменением состояния;
- raw books, PDF/EPUB/DJVU/MOBI и сырой текст источников не добавлены;
- private Drive URLs и file IDs не попали в репозиторий.

### Pass 2 — смысловая проверка

Проверить:
- PR не перескакивает workflow-стадии;
- draft не превращается в reviewed/approved без явного пользовательского разрешения;
- review-map не меняет сам draft без approval;
- новые правила не противоречат Своду, project-state и review-index;
- формулировки не создают ложного статуса вроде «источник прочитан», если есть только source card или placeholder;
- нет новой красивой риторики вместо реального правила.

### Если найдена ошибка

1. Оставить top-level comment в PR с пометкой `Self-review pass N` и коротким описанием проблемы.
2. Исправить проблему в той же ветке PR.
3. Повторно проверить PR после исправления.
4. Только после этого дать Сергею ссылку, статус mergeability и список того, что уже проверено.

Запрещено отдавать PR как готовый, если он не прошёл две проверки или если известная ошибка ещё не исправлена.

## Ограниченный auto-merge режим

ChatGPT может сам выполнить merge только для технического PR после обязательной двойной самопроверки.

Можно ускорять без дополнительного ручного действия Сергея:
- синхронизацию `project-state` и зеркала;
- исправление baseline/tests и CI-совместимости;
- обновление служебных протоколов, если они не меняют смысл книги, логику агентов или пользовательские материалы;
- реестры, индексы, ссылки, review queue и другие инфраструктурные файлы.

Нельзя мержить без явного согласия Сергея, если PR:
- меняет смысл книги, draft, reviewed chapter или approved chapter;
- меняет логику агентов, маршруты, guardrails или поведение системы;
- добавляет в материалы новые утверждения, позицию, голос, обещания или формулировки от имени Сергея;
- создаёт или меняет source card, training case, Свод, карту контекстов, MVP-документ или другой смысловой материал;
- переводит артефакт на следующую workflow-стадию;
- содержит спорную редакторскую, этическую, духовную, маркетинговую или продуктовую рамку.

Если категория PR смешанная, применяется более строгий режим: без явного согласия Сергея merge запрещён.

Если технический PR прошёл обе проверки, но вызов merge-инструмента блокируется не GitHub-ошибкой, а платформенным ограничением, ChatGPT фиксирует это как инструментальный блокер и передаёт Сергею ссылку для ручного merge.

## Как отвечать Сергею

В ответах нужно давать кликабельные ссылки на GitHub-файлы, а не только пути.

Файлы, которые нужно проверить или сравнить, указываются в формате `Название — URL`, а не только путём репозитория.

Для книжной работы в чате не нужно давать ссылки на каждый служебный слой, если Сергей должен читать только итоговый текст.

## Язык артефактов

- Технические metadata keys могут быть на английском.
- Human-readable content должен быть на русском.
- Reviewer-facing объяснения должны быть на русском.
- Reader-facing текст будущей книги должен быть на русском.

## Работа с книгами и источниками

- Полные книги не коммитить в GitHub.
- Сырой текст Плотникова не коммитить.
- PDF/EPUB/DJVU/MOBI не добавлять в репозиторий.
- Source card — это инвентарь, не сама книга.
- Если полного материала нет, агент не должен делать вид, что читал источник.
- Для полного материала использовать ручную загрузку фрагмента или приватный Google Drive.

## Работа с Плотниковым

Порядок обработки источника остаётся строгим:

1. manual upload одной главы или предисловия;
2. plotnikov map;
3. sync package;
4. user review;
5. использование в книге только как функция и контекст, не как форма.

Запрещено:

- пересказывать Плотникова;
- делать близкий рерайт;
- копировать структуру предисловия/главы;
- использовать длинные цитаты;
- строить нашу авторитетность на трофеях, доходах и «я успешный, слушай меня».

## Стиль проекта

- Не использовать выражение `христианское собрание` в книге.
- Использовать широкие формулировки: `духовная сфера`, `личные убеждения`, `пространство доверия`.
- `Каленчевский голос воодушевления` заменён на `Тихий Мастер`.
- Голос проекта: ясность, спокойная сила, границы, служение без давления.
- Введение — морковка, а не ранний разбор кухни MLM.
- В начале книги: сначала человек, узнавание и доверие; инструменты и термины — позже.

## Перезапуск чата

Если чат перегружен:

1. Новый чат не должен восстанавливать контекст по старой памяти.
2. Главный источник правды — GitHub.
3. Начинать с `assistant_codex_worklog/restart-prompt.md`.
4. Затем открыть:
   - `assistant_codex_worklog/current-state.md`;
   - `assistant_codex_worklog/roadmap.md`;
   - `assistant_codex_worklog/working-protocol.md`;
   - `assistant_codex_worklog/protocol_addenda/*.md`;
   - `knowledge/00_manifest/project-state.md`;
   - `knowledge/05_agent_memory/review_queue/review-index.md`.

Если перезапуск делается через prompt, который ChatGPT выдаёт в чате перед checkpoint, этот prompt должен быть до 6000 знаков с пробелами и не должен заменять собой файлы GitHub.

## Что делать после возвращения

1. Не начинать с нового PR по книге.
2. Продолжить Введение в чате с последнего принятого фрагмента.
3. Использовать агентов как внутренние редакторские слои.
4. После сильной читательской версии сделать один аккуратный GitHub PR для фиксации результата.
5. Для кода/агентов/реестров продолжать строгий PR workflow.
