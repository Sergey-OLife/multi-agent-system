# Decision Log — Assistant × Codex

Этот журнал фиксирует ключевые решения рабочего процесса Сергей ↔ ChatGPT ↔ Codex/GitHub.

## Решения

### 1. Не начинать новый чат с нуля

Решение: использовать `assistant_codex_worklog/` и проектные state-файлы как рабочие якоря.

Назначение: сохранить контекст взаимодействия Сергей ↔ ChatGPT ↔ Codex/GitHub без зависимости от памяти старого чата.

### 2. Отделить работу с Codex от книги

Решение: `assistant_codex_worklog/` хранит рабочий слой управления процессом, а не raw books и не черновики книги.

### 3. Главный источник правды — GitHub

Решение: новый чат восстанавливается по файлам репозитория, а не по памяти старого чата.

### 4. Все ответы с файлами должны содержать кликабельные ссылки

Решение: если Сергею нужно открыть, проверить или сравнить файл, давать кликабельную GitHub-ссылку, а не только путь.

### 5. Новая задача или текущий PR

Решение:

- если PR смержен — следующая веха обычно новая задача/ветка;
- если PR открыт и правим замечание reviewer — это ответ в текущий PR/ветку;
- если работа сделана, но PR не виден — создать PR из той же ветки, а не плодить дубль.

### 6. Google Drive для исходников

Решение: полные материалы держать в приватной библиотеке или в источниках проекта, не в GitHub.

Не грузить raw books, PDF/EPUB/DJVU/MOBI и сырой текст Плотникова в репозиторий.

### 7. Approval-gates

Решение: доступ к GitHub не равен разрешению на смысловое действие.

Явное approval Сергея требуется для:

- изменения смысла книги;
- изменения логики агентов;
- добавления материалов от имени Сергея;
- перехода артефакта на новую смысловую workflow-стадию;
- спорных этических, духовных, маркетинговых или продуктовых рамок.

### 8. Двойная самопроверка PR

Решение: каждый PR до передачи Сергею проходит два self-review прохода:

- технический: mergeable, не draft, ожидаемые файлы, state/tests sync, raw materials не попали в repo;
- смысловой: нет перескока стадий, нет ложного статуса, нет новой красивой риторики вместо правила.

Если ошибка найдена, сначала комментарий в PR, потом исправление в той же ветке, потом повторная проверка.

### 9. Ограниченный auto-merge

Решение: ChatGPT может пытаться мержить только технические PR после двойной самопроверки.

Если merge-инструмент требует ручного подтверждения интерфейса или блокируется платформенно, Сергей подтверждает/мержит вручную, а ChatGPT проверяет факт merge.

### 10. Введена команда checkpoint

Решение: команда `#checkpoint full` означает сохранить полную рабочую точку.

При таком checkpoint обновляются:

- `assistant_codex_worklog/current-state.md`;
- `assistant_codex_worklog/roadmap.md`;
- `assistant_codex_worklog/decision-log.md`;
- при необходимости `assistant_codex_worklog/working-protocol.md`;
- при необходимости `assistant_codex_worklog/restart-prompt.md`;
- при необходимости `knowledge/00_manifest/project-state.json` и зеркало `.md`.

### 11. Book Fast Track

Решение от 2026-05-17: разделить технический workflow и книжный workflow.

Проблема: строгая GitHub-цепочка `draft → review-map → revised draft → reviewed → approved` заставила Сергея читать почти один и тот же текст несколько раз и замедлила написание книги.

Новое правило:

- код, агенты, маршруты, guardrails, registries, tests и project-state — через строгий PR workflow;
- главы книги — сначала быстрый редакторский цикл в чате;
- агенты используются как внутренние редакторские слои внутри ответа, а не как отдельные GitHub-артефакты на каждый шаг;
- GitHub фиксирует уже принятый результат, а не каждую промежуточную мысль;
- reviewed/approved стадии для глав не плодятся автоматически, если они лишь дублируют один и тот же текст.

### 12. Текущее состояние Введения

PR #24 смержен: создан `book/02_reviewed/chapter_00_preface.md`.

Но дальнейшая работа над Введением продолжается в чате как над читательской версией без metadata и служебных блоков.

Приняты решения:

- Заголовок: `От автора: перед входом`.
- Начало: `Эта книга не обещает чудо — она даёт карту. И начинается с отказа.`
- Формула: `Она не обещает, что вы быстро решите финансовые вопросы.`
- Введение — морковка, а не ранний разбор кухни MLM.
- В начале не перегружать читателя языком продаж.
- Принята формула: `В деле, где один человек приглашает другого идти рядом, доверие становится рабочей зоной ответственности.`

Следующее действие после возвращения: продолжить Введение в чате с последнего принятого фрагмента, не начинать с нового PR.

### 13. Source Intake Audit и автономное создание агентов

PR #26 смержен: в `working-protocol.md` добавлены правила Source Intake Audit и создания агентов из источников/логики проекта.

Решение:

- новый источник не считается рабочим только потому, что он назван;
- источник становится рабочим, когда есть материал, карточка, роль и правило применения;
- при аудите проверяются Drive/source locations, дубли, пустые оболочки, карточки, статус пригодности, `usage_role`, `allowed_use`, `forbidden_use`, `book_zones`, `agent_layers`, `next_action`;
- ChatGPT может создавать отдельных агентов в любой момент, если этого требует логика проекта или это значительно улучшает работу;
- число агентов не ограничено, ограничение только процессное: агент не должен плодить хаос, дублировать существующую роль или тормозить работу;
- если агент меняет маршруты, guardrails или поведение системы, требуется явное approval Сергея перед merge.

### 14. Загружена первая большая волна источников проекта

Сергей загрузил в источники проекта «Пишем книгу» большую волну материалов: КПТ/Бек, сократический метод, эмоции, влияние, драматический треугольник, SuperBetter и ключевые проектные документы (`Svod v4.1`, `Plotnikovsky Motor`, `Karta Kontekstov Istochnikov`, `MVP v1.1`, пакет обновления и др.).

Решение:

- считать эти материалы загруженным сырьём, а не автоматически проаудированной библиотекой;
- следующий технический блок: `Source Intake Audit: первая волна проектных источников`;
- параллельно можно продолжать Введение в Book Fast Track, не начиная новый PR по книге;
- использовать проектный чат как рабочую комнату для книги, источников, агентов, GitHub-логики, Google Drive-библиотеки и MVP.

### 15. Короткие команды Сергея: `+` и `++`

PR #39 смержен: введено правило коротких команд.

Решение:

- `+` означает продолжить следующий логичный безопасный шаг по текущему плану;
- `+` не является approval;
- `++` означает approval текущего понятного approval-gate;
- если approval-gates несколько, нужно уточнение;
- если пользователь пишет номер PR вместе с `++`, например `41 ++`, это approval именно этого PR.

### 16. Автоматическая проверка mergeability

PR #42 смержен: перепроверка mergeability открытого PR не требует отдельного подтверждения Сергея.

Решение:

- ChatGPT сам проверяет mergeability после создания PR, перед просьбой о `++`, после `+`, после `++` перед merge и если PR был открыт несколько шагов назад;
- проверка mergeability не является approval;
- для merge по-прежнему нужен `++`, если PR попадает под approval-gate;
- protocol addenda подключены к restart path через `restart-prompt.md` и `working-protocol.md`.

### 17. Restart prompt перед checkpoint full

Решение: перед выполнением `#checkpoint full` ChatGPT обязан сначала прислать Сергею корректный restart prompt для следующего чистого чата.

Checkpoint не начинается, пока restart prompt не отправлен в чате.

### 18. `socratic_lantern_agent` активирован как optional workflow layer

PR #40 смержен.

Решение:

- `socratic_lantern_agent` активен как optional workflow layer;
- не hard guardrail;
- не route-required;
- рабочая формула: `Вопрос — это фонарь, а не поводок`;

- если применение слоя может изменить направление работы, структуру главы или удалить сильную, но рискованную сцену, ChatGPT сначала делает конкретное предложение в чате.

### 19. `ethical_persuasion_guard` вместо анти-маркетингового фильтра

PR #41 смержен: создан proposal `ethical_persuasion_guard`.

Решение Сергея: красиво упакованное влияние должно работать на воодушевление и убеждение. Давление допустимо, если оно конструктивное.

Решение системы:

- не делать агента стерильным анти-маркетинговым фильтром;
- главная формула: `Оставить огонь. Убрать дым`;
- сохранять убеждение, CTA, предпринимательский импульс и конструктивное давление;
- отсекать вину, страх, ложную срочность, давление на семью/здоровье/духовность, авторитет без проверки и обещания без основания.

### 20. Чалдини используется как risk map, не как учебник давления

PR #43 смержен.

Решение:

- `cialdini_influence` используется как карта рисков влияния;
- не использовать Чалдини как источник продающих крючков, обхода сопротивления или усиления FOMO;
- принципы влияния допустимы, если помогают человеку увидеть реальность яснее;
- недопустимы, если заставляют реагировать быстрее, чем человек успевает подумать.

### 21. Для здоровья/Olife действует medical caution audit

PR #43 смержен.

Решение:

- в текстах про здоровье влияние должно вести к ответственной проверке, а не к слепой покупке;
- не использовать диагноз, страх за семью, обещания лечения, «подходит всем», «натуральное значит безопасное»;
- допустимая логика: проверить состав, ограничения, состояние, лекарства, противопоказания, проконсультироваться со специалистом при необходимости, начать с малого и наблюдать реакцию.
